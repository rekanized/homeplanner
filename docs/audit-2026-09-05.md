# Application audit — 5–6 September 2026

The audit found and fixed functional, validation, navigation, accessibility, and responsive defects. The final automated suite passes **84 tests / 300 assertions**. The populated browser page matrix passes **120 page/viewport combinations**, with HTTP 200 responses, no captured console errors, and no elements extending horizontally outside the viewport. A separate final template-modal check passes at four widths.

## Environment and scope

Testing used actual Chromium browser interaction through the existing Playwright installation, local Laravel servers, and a freshly migrated disposable SQLite database. Upload workflow tests used separate temporary storage. No production household records were changed, no migrations were changed, and no dependencies were installed.

**The shared VS Code browser was not available through this session's tools**, including after the user enabled Sharing with Agent. Consequently, these results describe isolated local browser testing, not interaction with the shared browser. The live site's anonymous login page also returned HTTP 200 without a captured JavaScript exception; authenticated production workflows were not exercised.

## Issues found and fixes made

| Issue | Fix and verification |
| --- | --- |
| A mixed-case duplicate user email passed validation and caused a database error. Login handling was inconsistent with normalized stored addresses. | Normalize email before validation/login; duplicate creation now gives validation feedback, and uppercase login succeeds. |
| Todo tag filters leaked between lists, hiding tasks on the newly selected list. | Clear selected tags/items when changing, creating, or deleting lists; browser and component regressions cover switching. |
| Category renaming could produce an unhandled duplicate-name error and leave expenses associated with the old text. | Validate uniqueness inline and transactionally rename matching expense category values; totals/grouping remain correct. |
| Repeated Member/Child clicks toggled the role instead of setting the requested value. | Explicit, idempotent role-setting actions with pressed state; master-user protections remain covered. |
| Switching monthly and weekly templates mixed scalar and array recurrence values; invalid schedules lacked useful feedback. | Reset day state on strategy changes, validate day values by recurrence type, and normalize saved/edit state. |
| Unsupported proof uploads caused an error while generating a preview, before submit validation. | Validate uploads before preview rendering, clear invalid files, and permit recovery with a valid image. Submission validation remains in place. |
| Several Kids forms silently failed validation or reopened with stale errors/state. | Display missing errors and reset relevant modal validation/editor state. |
| Chore templates were inaccessible from the mobile header. | Expose Templates on mobile and allow header actions to wrap. |
| Long list names and user/child names overflowed or clipped controls, cards, and the template assignee picker. | Constrain flexible children, truncate list selectors, and wrap long names. Verify populated pages and open template modal separately. |
| Template assignee selectors were clickable divs. | Use buttons with pressed state; keyboard selection and persisted creation pass in Chromium. |
| Directly loaded Kids/Admin layouts omitted the existing app script, losing its accessibility behavior. | Restore the script, favicon, skip link, and main target in that layout; direct navigation and labeled modal controls verified. |
| Ordinary members saw Admin links leading to forbidden pages; module navigation remained stale after saving settings. | Match navigation visibility to admin authorization and refresh the sidebar on module updates. Browser role/module checks pass. |
| Google token/user-info connection failures could surface as server errors. | Return to login with actionable feedback. Mocked network-failure tests cover both requests. |
| An apostrophe in an allowed email broke its removal action's JavaScript argument. | Encode the argument with Blade's JavaScript encoder; add/remove flow verified. |
| Admin authentication help, upload-size help, version display, and the authentication anchor were inaccurate or incomplete. | Align copy with actual behavior, show the version from the existing source, add the anchor and missing field error, and update affected Swedish strings. |
| Template rendering queried assigned users repeatedly despite already loading children. | Reuse the loaded child collection for template summaries and selectors; render/create/reload verified. |

## Browser testing performed

All twelve signed-in pages were opened directly: Home, Economy, Savings, Monthly History, Savings History, Shopping, Todo, Kids, Users, Settings, Audit Log, and Application History. Empty-state and populated passes were separate. Stress fixtures included 150 shopping items, 150 tasks, 250-character list names, and a 255-character child name.

Actual interactions included:

- Initial manual setup, login validation, normalized login, logout, protected redirects, invalid OAuth callback state, and a missing-page response.
- Shopping list/item creation and editing, quantities, completion, clearing, sorting, persisted mouse drag ordering, deletion, and confirmation cancellation.
- Todo creation/editing, due dates, tags, list filtering, completion/reversion, deletion, and cancellation.
- Income, monthly savings, expense and savings-goal editing; category validation/rename; payer, split and delay controls; both snapshot create/view/delete flows.
- Chore assignment/completion, points validation/redemption, template strategy switching and validation, and template creation/editing.
- Child photo upload; parent viewing, rejection, resubmission and approval; guest proof redirect; invalid-file feedback and valid-file recovery.
- User role selection, modal validation, parent impersonation and return, child/member admin denial, module toggles, allowed-email editing, log pagination and page size.
- Navigation, direct URLs, modal open/close, theme persistence, English/Swedish switching, refresh, and browser back/forward.

The five core CRUD/pagination groups passed at both 390×844 and 1440×900, without captured browser errors. The photo workflow used parent desktop and child mobile contexts. There is no general search field to test; available filtering, sorting, and pagination were exercised.

## Responsive testing

The final twelve-page populated matrix covered:

- Desktop: 1920×1080, 1440×900, 1366×768, 1280×720.
- Mobile: 390×844, 375×667, 360×800, 412×915.
- Tablet: 768×1024.
- Landscape: 844×390.

Screenshots were inspected alongside geometry checks. Root-width checks alone missed some clipped descendants during the audit, so descendant bounds and a separate modal scroll-width check were also used. After the final template edit, keyboard selection, save/reload, and internal modal overflow checks passed at widths 360, 390, 768, and 1440. The 120-page matrix measures page states; it does not imply every modal/action was repeated at all ten sizes.

## Remaining concerns and useful follow-up

- The specifically requested shared-browser verification remains outstanding because no connection was exposed to the agent. Repeat the critical authenticated flows in that browser when access is available.
- Complete one real Google OAuth sign-in against the deployment's configured credentials; mocked responses and an invalid callback do not verify provider configuration.
- Verify deployment upload limits support the advertised 5 MB application limit. The isolated upload server used explicit PHP limits; the deployed PHP-FPM/proxy limits were not verified.
- Native phone camera/touch behavior and Safari/Firefox were not tested. Some compact controls are below a 44-pixel touch target, although the tested mobile flows were usable in Chromium.
- This was not a load or concurrency test. Parallel points changes, concurrent scheduler execution, interrupted requests, and month-boundary execution on the deployed worker still warrant operational checks; feature tests cover scheduled business logic only.
- The application retains its existing shared-household data model. The review does not establish independent household tenancy or certify the absence of all security defects.

Changes are left in the working tree for review; no commit or deployment operation was performed.
